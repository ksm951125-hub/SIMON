# CODEX AUTO CONTINUE

Windows 11 에서 **GPT Codex** 와 **Claude Code** 데스크톱 앱이 **사용량 제한**으로 멈췄을 때, 각 앱 화면에 표시된
**실제 초기화 시각 + 2분**에 **사용자가 지정한 기존 대화**에 `계속` 을 자동 전송해 작업을 이어가게 하는 백그라운드 도구입니다.
두 앱은 서로 다른 시각(예: Codex 오후 10:47, Claude 오후 11:50)에 초기화되므로 **앱마다 독립된 주기·이력으로** 처리합니다.
(기존 MY AI OFFICE / AI STUDIO 프로젝트와 완전히 독립. 외부 서비스·비공개 API·인증정보·제한 우회 없음)

> **⚠ 먼저 읽어 주세요 — 검증 범위**
> 이 프로그램은 Linux 클라우드 세션에서 작성되어 **실제 Windows / 실제 Codex 앱 / 첨부하신 스크린샷으로는 검증하지 못했습니다.**
> 시간 해석·감지·중복 방지·재시작 복원·안전장치 등 **핵심 로직은 가상 앱으로 자동 테스트(93개)를 통과**했고,
> 보내주신 스크린샷의 화면 구조(Codex 하단 카드/대화 기록 오류 줄/사이드바, Claude Code 토스트/사이드바)를 모사한 가짜 UI 트리로도 검증했습니다.
> 그러나 실제 앱의 UI 트리에 붙는 **Windows UI Automation 어댑터는 실제 PC 에서 실행해 보지 못했습니다.**
> 따라서 **처음 한 번 `inspect.cmd` → `--dry-run` 순서로 확인**한 뒤 실전송을 켜 주세요. (아래 "처음 사용 순서")

## 1. 빠른 시작

```
install_to_documents.cmd   (선택) 문서\1_개발\CODEX_AUTO_CONTINUE 로 복사
start.cmd                  최초 1회 .venv 생성 + 라이브러리 설치 후 트레이로 실행
```
| 파일 | 용도 |
|---|---|
| `start.cmd` | 콘솔 없이 트레이/관리 화면 실행 (`--dry-run`, `--test-mode` 옵션 전달 가능) |
| `start_console.cmd` | 콘솔에서 로그를 보며 실행 (문제 확인용) |
| `inspect.cmd` | **STEP 1 환경 분석**: Codex 프로세스/창/UI 요소 덤프 + 감지기가 읽은 결과 (읽기 전용) |
| `run_tests.cmd` | 자동 테스트 (Codex 에 아무것도 전송하지 않음) |
| `build_exe.cmd` | (선택) 단일 exe 빌드 |
| `setup.cmd` | 가상환경/라이브러리 설치 |

요구 사항: Windows 10/11, Python 3.9+ (python.org). 라이브러리: pywinauto, psutil, pystray, Pillow.

### 기본 감시 대상 (스크린샷 기준 — 바꾸려면 관리 화면 "감시 대상 대화 선택")
| 프로필 | 앱 | 프로젝트 / 대화 | 기본 |
|---|---|---|---|
| `codex` | GPT Codex | `AI STUDIO` / `점검 OCI 이전 준비` (한도 오류 표시가 붙어 있던 대화) | 켜짐 |
| `claude` | Claude Code | `1_블로그포스팅` / `네이버 블로그 AI 포스팅 생성기 (fork)` | 켜짐 |
| `codex-myai` | GPT Codex | `AI STUDIO` / `MY AI OFFICE 구축하기` | **꺼짐** (필요하면 `data\config.json` 에서 `"enabled": true`) |

> Codex 쪽 기본 대상은 스크린샷에서 한도 오류(!) 표시가 있는 `점검 OCI 이전 준비` 로 잡았습니다. 처음 말씀하신 `MY AI OFFICE 구축하기` 를 쓰시려면 `codex-myai` 를 켜거나 대상 대화를 바꾸세요. 같은 앱의 여러 대화는 순차 처리됩니다.

### 처음 사용 순서 (권장)
1. Codex 와 Claude Code 를 실행하고 각 대상 대화를 연 상태에서 `inspect.cmd` 실행 (프로필별로 출력)
   - ① 앱 프로세스/창이 잡히는지, ② `data\inspect\uia_tree_*.txt` 에 요소가 충분히 있는지,
   - ③ "활성 대화 후보"에 대상 대화 제목이 나오는지, ④ "대상 대화 식별: OK" 인지 확인.
   - 프로세스 이름이 다르면(`process_names`) `data\config.json` 의 해당 프로필에서 수정.
2. `start.cmd --dry-run` 으로 실행 → 실제 제한이 걸렸을 때 로그에 `[DRY RUN] ... 전송 조건 충족` 이 찍히는지 확인.
3. 정상이면 `--dry-run` 없이 `start.cmd`. 설정에서 "Windows 로그인 시 자동 실행" 체크.

`--test-mode` 는 가상 Codex 로 **제한 → 초기화 → 재개 → 다음 제한** 반복을 몇 분 안에 눈으로 볼 수 있습니다
(`start.cmd --test-mode`, 시나리오: `--scenario wrong-conversation|user-typing`). 실제 Codex 와 무관하며 별도 폴더(`data\test_mode`)를 씁니다.

## 2. 자동화 동작 방식

```
감시(15초) ─ 제한 안내 감지 ─▶ 초기화 시각 파싱(KST) ─▶ 재개 시각 = 초기화 + 2분 ─▶ (상태 저장) 대기
   ▲                                                                              │ 재개 시각 도달
   │            ┌──────────────── 안전 확인(모두 통과해야 전송) ◀──────────────────┘
   │            │ 인터넷 / UI 사용 가능(잠금·절전 아님) / 최소화 복원 / 제한 해제 여부 /
   │            │ 대상 대화 식별(필요 시 사이드바에서 기존 대화 선택) / 이미 작업 중 아님 /
   │            │ 입력창에 사용자 작성 글 없음 / 직전 전송 후 최소 간격
   │            ▼
   └── 전송 → 5초 후 재확인(입력창 비움·작업 시작 여부) → 이력 저장(중복 방지) → 다음 제한 대기
```
- **화면 문구 인식** (스크린샷 기준): Codex 하단 카드 "Codex 및 Work 사용량을 모두 사용했습니다 … 오후 10:47에 사용량이 재설정될 때까지", Codex 대화 기록의 "사용 한도에 도달했습니다 … 오후 10:47에 다시 시도하세요", Claude Code 알림 "사용량 제한을 초과하여 종료됨 / 오후 11:50에 초기화".
  - **현재도 제한 중인 카드(live)** 와 **대화 기록에 남은 지난 오류 줄/이미 지난 알림**을 구분합니다. 초기화 후에도 기록 줄은 남아 있으므로, 이를 '제한 유지'로 오판해 영원히 대기하는 일이 없고, 이미 초기화된 기록 줄만 보고 새 주기를 만들지도 않습니다.
  - Claude Code 알림은 **닫아도(X) 이미 저장된 주기는 유지**됩니다(감지 시점에 저장하므로). 단, 알림이 뜨고 사라지는 사이에 감시 주기(15초)보다 짧게 보였다면 놓칠 수 있습니다.
- **초기화 시각은 화면 문구에서 읽습니다.** 5시간 고정 타이머 없음. `오전/오후`, 24시간, `11시 35분`, `내일`, `10월 25일`, `2시간 15분 후`, 영문 표기 지원. 자정 넘김(23:50 에 "오전 12:10" → 다음 날) 처리. 시각이 바뀌면 새 시각으로 갱신.
- **초기화 시각이 지났는데도 안내가 남아 있으면** 보내지 않고 2분 간격으로 재확인. 안내 시각이 바뀌면 그 시각 기준으로 다시 대기.
- **중복 전송 방지** (여러 겹): 초기화 주기별 1회(이력 `data\state.json` 에 영속) · 전송 시작 전 "전송 중" 기록(전송 도중 종료돼도 재전송 안 함) · 결과 확인 불가 시에도 재전송 안 함 · 실전송 간 최소 10분 · 중복 실행 잠금(프로그램 2개 동시 실행 차단).
- **잘못된 곳에 입력되지 않도록**: 대상 대화가 **현재 활성 대화로 확인될 때만** 전송. 확인 실패 시 전송하지 않고 로그에 오류 기록. 키보드 방식은 사용자가 20초 이상 입력이 없을 때만, 창을 앞으로 가져온 뒤 **포커스 창이 Codex 인지 재확인**하고, 입력값 확인 후 Enter. 하나라도 어긋나면 중단.
- **전송 방식 `auto`**: ① UIA ValuePattern 으로 입력 + 전송 버튼 Invoke (포커스·마우스를 건드리지 않음). 단 '빈 입력창에서 전송 버튼이 비활성 → 입력 후 활성'으로 앱이 실제 반영했음이 확인될 때만 사용 → 아니면 ② 사용자가 20초 이상 입력이 없을 때 키보드 방식(대상 창 포커스 재확인 후 입력, Enter). Electron 기반 입력창(Codex/Claude)은 ①이 안 먹는 경우가 많아 ②로 동작할 가능성이 큽니다. 좌표 클릭은 사용하지 않습니다.
- 예외 처리: Codex 종료(실행될 때까지 대기) · 최소화(포커스 없이 복원) · 사용자가 다른 프로그램 사용 중(UIA 방식은 포커스 불변, 키보드 방식은 보류) · 잠금 화면/절전(조작 안 함, 복귀 후 재확인) · 절전 복귀(20초 안정화 후 재확인) · 인터넷 끊김(보류) · UI 구조 변경(요소를 못 읽으면 재시도 후 포기, 로그) · 사용자가 먼저 재개/작업 중(전송 취소) · 입력창 초안 있음(덮어쓰지 않음) · 프로그램 재시작(진행 중 주기 복원) · 12시간 넘은 오래된 주기 폐기.

## 3. 관리 화면 / 트레이
앱별 한 줄 표(앱·감시 대화·앱 상태·초기화·자동 재개·남은 시간·마지막 실행·자동화 ON/OFF) + 선택한 앱의 상세(프로젝트·현재 동작·마지막 전송 시각·마지막 오류)와
버튼(전체 시작 / 전체 일시정지 / 선택 앱 켜기·끄기 / 감시 대상 대화 선택 / 실행 로그 / 설정 / 종료). 창을 닫으면 트레이로 숨김(트레이 색: 초록=정상, 주황=제한/대기, 회색=일시정지).
CLI: `python -m codex_auto_continue [gui|run|once|inspect|set-target|autostart|history|reset] [--profile codex|claude]`.

## 4. 설정 (`data\config.json`, 첫 실행 시 자동 생성)
최상위 키는 **모든 앱 공통**(`resume_delay_minutes`(2) · `poll_interval_seconds` · `send_method`(auto/uia/keyboard) · `idle_required_seconds`(20) ·
`require_project_match` · `match_mode`(exact/contains) · `completion_markers` · `dry_run` …), `profiles` 배열이 **앱별 설정**입니다
(`name`, `label`, `app`(codex/claude), `enabled`, `target`{project, conversation}, `process_names`, `window_title_regex`, `selectors` …; 프로필에 적은 값이 공통값보다 우선).
`selectors`: 전송/중지 버튼 이름, 작업 중 문구 정규식, 입력창 placeholder, 하단 안내 영역 높이(`banner_zone_px`), 사이드바 폭 비율(`sidebar_ratio`) —
**실제 앱에서 감지가 안 되면 `inspect` 결과를 보고 해당 프로필의 `selectors` 를 조정**하세요.
Codex/Claude 가 UIA 요소를 거의 노출하지 않으면 Chromium 접근성이 꺼진 것일 수 있습니다. 그 경우 앱을 `--force-renderer-accessibility` 옵션으로 실행해 보세요(이 프로그램은 앱 실행 방식을 바꾸지 않습니다).

2분 지연 정확성 · 반복 주기 · 시각 변경 · 제한 유지 · 잘못된 대화 차단 · 사용자 초안 보호 · 이미 작업 중 취소 · 중복 방지 · 재시작 복원 · 일시정지 · Dry Run · 잠금/절전/네트워크/최소화/미실행 · 전송 실패 재시도/포기/확인 불가 ·
**스크린샷 시나리오**(Codex 카드+기록 줄, Claude 토스트 닫힘, 지난 기록 줄 무시, 두 앱이 각자 시각에 1회씩 전송, 다른 대화가 열려 있을 때 대상 대화로 전환, 프로필 설정 저장/마이그레이션/손상 복구) ·
스크린샷 구조를 흉내 낸 가짜 UIA 트리로 화면 해석·대화 식별(같은 프로젝트의 다른 대화/다른 프로젝트 거부) 검증.
안전장치(대화 식별, 입력 초안 보호, 중복 방지, 지난 기록 줄 무시)를 일부러 제거하면 해당 테스트가 실패함을 확인했습니다.

## 6. 알려진 한계 / 미구현
- **실제 앱 UI 로 미검증** (위 경고). 요소 이름·전송 버튼 이름·"작업 중" 표시·실행 파일 이름(`codex`, `claude`)은 추정 기본값이며 `inspect` 로 보정 필요. 프로젝트 확인은 '사이드바에서 활성 항목 바로 위 항목들'로 추정하므로, 구조가 다르면 `require_project_match: false` 로 대화 제목만 확인하게 할 수 있습니다.
- **OCR/이미지 분석 미구현**: UIA 로 텍스트가 안 읽히는 경우의 보조 수단은 넣지 않았습니다(`Snapshot.banner_texts` 에 공급자를 연결하면 확장 가능).
- 트레이로 완전히 숨겨진(보이지 않는) 앱 창은 찾지 못합니다. 작업 표시줄에 최소화된 상태는 지원.
- 같은 이름의 대화가 여러 개이면 특정할 수 없어 전송하지 않습니다(프로젝트명으로 구분 시도).
- 대화 본문에 "요청 한도는 오전 11:35에 재설정됩니다" 같은 문구가 인용돼 보이면 오감지할 수 있음 → 전송 전 "제한 해제 확인"에서 걸러져 **잘못 전송되지는 않지만** 해당 주기는 대기만 합니다. 안내 영역을 창 하단으로 한정해 완화.
- Windows 에 로그인되어 **화면이 잠기지 않은 상태**여야 합니다. 잠금/절전 중에는 조작하지 않고 복귀 후 재개합니다.
- 앱마다 대화 1개가 기본입니다. 같은 앱의 여러 대화는 프로필을 추가해 쓸 수 있으나 순차 처리되며, 한도 안내가 계정 공통으로 보이면 켜 둔 프로필 모두에 '계속'이 전송됩니다(지정한 대화만 켜세요).
- 키보드 방식은 "확인 후 입력" 사이의 극히 짧은 시간에 사용자가 타이핑하면 이론상 간섭 가능 → 유휴 20초 조건과 직전 재확인으로 최소화.
